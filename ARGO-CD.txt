WHAT IS ARGO CD ARCHITECTURE?
-----------------------------

Argo CD follows the GitOps approach, where Git is the single source of truth.

The user makes changes only in Git, and those changes are used to deploy the
desired application state to the Kubernetes cluster.

We have two main components of Argo CD:
1. Application Controller
2. Repo Server

Repo Server gets the configuration from Git, while Application Controller
compares the Git state with the actual cluster state and reconciles differences.

If someone makes a manual change directly in the Kubernetes cluster, it is not
considered the source of truth.

Argo CD detects the difference and, when self-healing/synchronization is enabled,
brings the cluster back to the state defined in Git.

In our GitOps model, deployment changes should come from the Git side,
not from manual cluster-side changes.


ARCHITECTURE
------------

Repo Server:
It connects to Git and gets the state/configuration from Git.

You can consider it as a microservice that talks to Git.

Application Controller:
It talks to Kubernetes and gets the state of Kubernetes.

We need Repo Server and Application Controller to get the state between
Git and Kubernetes.

One microservice gets the state from Git, and another microservice gets
the state from Kubernetes.

Then both states are compared.

Repo Server State = Application Controller State
                  ↓
            If required, deploy/reconcile


UI / CLI
--------

Argo CD is a UI/CLI-based solution.

A user tries to connect to Argo CD using the UI or CLI.

There is a component called API Server, which is used by the user to
communicate with Argo CD through UI and CLI.

API Server handles authentication.

Argo CD also supports Single Sign-On and integration with OIDC providers
and external identity systems.

For this, Argo CD comes with Dex Server.


REDIS
-----

Redis is used for caching.

If the Application Controller goes down and later comes back up,
Redis helps with cached information/state.

Redis is used to avoid repeatedly doing expensive work.

Concrete things it caches can include frequently accessed or
computed information.


HOW TO WALK THROUGH ARGO CD ARCHITECTURE
----------------------------------------

1. UI / CLI
   The student or engineer opens the dashboard or types an Argo CD command.

2. API Server
   Every request lands here first.
   It is the main entry point.

3. Dex
   Handles login/authentication.

4. Redis
   Caches information so repeated requests are faster.

5. Repo Server
   Pulls raw manifests from Git.
   Processes Helm/Kustomize templating.
   Renders the final YAML.

6. Application Controller
   Takes the rendered YAML, compares it with what is actually running
   in Kubernetes, and applies the difference.

KEY TEACHING POINT:
The Repo Server mainly talks to Git, and the Application Controller
talks to Kubernetes. Each component has its own responsibility.


END-TO-END FLOW
---------------

1. User changes YAML in GitHub
2. Repo Server gets YAML from GitHub
3. Application Controller gets the desired state
4. Application Controller checks Kubernetes
5. It compares Git state with cluster state
6. If both are the same → Everything is OK
7. If they are different → Argo CD detects the difference
8. Argo CD reconciles the cluster with Git
9. Kubernetes runs the desired application state


WHAT IS ARGO CD?
----------------

Argo CD is a GitOps continuous delivery tool for Kubernetes.

It continuously checks the configuration stored in Git and compares it
with the actual state of the Kubernetes cluster.

Git = Desired State / Source of Truth
Kubernetes = Actual State


WHAT IS GITOPS?
---------------

GitOps is a methodology where Git is used as the single source of truth
for the desired state of applications and infrastructure.

In our Kubernetes environment, developers make configuration changes in Git,
and Argo CD automatically detects those changes and synchronizes the
Kubernetes cluster with the desired state defined in Git.


GITOPS
------

WHAT IS GITOPS?
GitOps uses Git as a single source of truth to deliver application
and infrastructure.

It is not only for application deployment.
It is also used for infrastructure deployment.

Example:
If we increase a resource in Kubernetes and after 10 days someone asks
what changes were made in Kubernetes, without GitOps we may not have
a proper track of those changes.

If we have hundreds of Kubernetes clusters and hundreds or thousands
of applications to manage, GitOps helps us manage them consistently.


GITOPS PRINCIPLES
-----------------

1. Declarative
2. Versioned and Immutable
3. Pulled Automatically
4. Continuously Reconciled


CONTINUOUS RECONCILIATION
-------------------------

Git continuously tracks the desired changes.

Suppose someone goes directly to the Kubernetes cluster and modifies
a resource.

GitOps says that Git is the single source of truth.

To make a change to a resource managed by GitOps, the change should first
be made in the Git repository and then deployed.

GitOps is there to overwrite/reconcile unwanted cluster-side changes.

GitOps continuously watches the Kubernetes cluster and keeps track
of Kubernetes resources.

The controller gets information about Kubernetes resources and keeps
a cache of that information.


REPO SERVER
-----------

The Repo Server connects to GitHub and gets the application
configuration/YAML files.

The Argo CD Repo Server is responsible for:
- Connecting to Git repositories
- Retrieving application configuration
- Generating/rendering Kubernetes manifests

Flow:

Repo Server
    ↓
Connects to Git
    ↓
Gets Application Configuration


APPLICATION CONTROLLER
----------------------

The Application Controller continuously monitors applications,
compares the desired state from Git with the actual state in Kubernetes,
and reconciles any differences.


GIT = SOURCE OF TRUTH
---------------------

Git says what SHOULD BE RUNNING.

Kubernetes shows what IS CURRENTLY RUNNING.


WHAT HAPPENS IF SOMEONE CHANGES KUBERNETES MANUALLY?
----------------------------------------------------

Git is the source of truth.

A manual cluster change does not become the desired state in Git.

Argo CD detects the difference and, when reconciliation/self-healing
is enabled, restores the cluster to the Git-defined state.


API SERVER IN ARGO CD
---------------------

The API Server is the main entry point of Argo CD.

Whenever a user interacts with Argo CD using the Web UI or CLI,
the request first comes to the API Server.


COMPLETE WORKFLOW
-----------------

Redis is the caching component of Argo CD.

STEP-BY-STEP ARGO CD INSTALLATION PROCESS
------------------------------------------

IMPORTANT
---------

Before installing Argo CD, we need a Kubernetes cluster.

I am using an Ubuntu Server running on AWS EC2.

We can also use another cloud provider.

For this practice, I am creating a SINGLE-NODE Kubernetes cluster
on the Ubuntu EC2 instance.

Also add an inbound rule for port 30437.


EC2 INSTANCE REQUIREMENT
------------------------

The EC2 instance should have at least 2 GB RAM and 15 GB storage.

For Argo CD practice, choose the EC2 instance type carefully.

If the instance has insufficient RAM, Kubernetes installation can fail.

In my first attempt, kubeadm failed because the machine had only
908 MB RAM available.


STEP 1 - CREATE KUBERNETES SHELL SCRIPT
---------------------------------------

Create the shell script:

vi k8setup.sh

Explanation:
This creates/opens the Kubernetes installation shell script.

Give executable permission:

chmod u+x k8setup.sh

Explanation:
This gives the current user permission to execute the shell script.

Run the script:

./k8setup.sh

Explanation:
This executes the complete Kubernetes installation process.


KUBERNETES INSTALLATION SHELL SCRIPT
-------------------------------------

Copy the following into:

k8setup.sh

#!/bin/bash

set -e

# 1. UPDATE UBUNTU

sudo apt update
sudo apt upgrade -y

# 2. INSTALL CONTAINERD

sudo apt install -y containerd

# 3. CONFIGURE CONTAINERD

sudo mkdir -p /etc/containerd

containerd config default | sudo tee /etc/containerd/config.toml > /dev/null

sudo sed -i 's/SystemdCgroup = false/SystemdCgroup = true/' /etc/containerd/config.toml

sudo systemctl restart containerd
sudo systemctl enable containerd

# 4. DISABLE SWAP

sudo swapoff -a
sudo sed -i '/ swap / s/^/#/' /etc/fstab

# 5. LOAD KUBERNETES KERNEL MODULES

cat <<EOF | sudo tee /etc/modules-load.d/k8s.conf
overlay
br_netfilter
EOF

sudo modprobe overlay
sudo modprobe br_netfilter

# 6. CONFIGURE KUBERNETES NETWORKING

cat <<EOF | sudo tee /etc/sysctl.d/k8s.conf
net.bridge.bridge-nf-call-iptables=1
net.bridge.bridge-nf-call-ip6tables=1
net.ipv4.ip_forward=1
EOF

sudo sysctl --system

# 7. INSTALL REQUIRED PACKAGES

sudo apt install -y apt-transport-https ca-certificates curl gpg

sudo mkdir -p -m 755 /etc/apt/keyrings

# 8. ADD KUBERNETES REPOSITORY

curl -fsSL https://pkgs.k8s.io/core:/stable:/v1.34/deb/Release.key | \
sudo gpg --dearmor -o /etc/apt/keyrings/kubernetes-apt-keyring.gpg

echo "deb [signed-by=/etc/apt/keyrings/kubernetes-apt-keyring.gpg] https://pkgs.k8s.io/core:/stable:/v1.34/deb/ /" | \
sudo tee /etc/apt/sources.list.d/kubernetes.list

# 9. INSTALL KUBERNETES COMPONENTS

sudo apt update

sudo apt install -y kubelet kubeadm kubectl

sudo apt-mark hold kubelet kubeadm kubectl

sudo systemctl enable kubelet

# 10. INITIALIZE KUBERNETES CLUSTER

sudo kubeadm init --pod-network-cidr=192.168.0.0/16

# 11. CONFIGURE KUBECTL

mkdir -p $HOME/.kube

sudo cp /etc/kubernetes/admin.conf $HOME/.kube/config

sudo chown $(id -u):$(id -g) $HOME/.kube/config

# 12. INSTALL CALICO NETWORK

kubectl apply -f https://raw.githubusercontent.com/projectcalico/calico/v3.30.3/manifests/calico.yaml

# 13. ALLOW PODS ON CONTROL-PLANE

kubectl taint nodes --all node-role.kubernetes.io/control-plane- || true

# 14. WAIT FOR KUBERNETES

echo "Waiting for Kubernetes node to become Ready..."

sleep 30

# 15. CHECK KUBERNETES

echo "===== KUBERNETES NODES ====="

kubectl get nodes

echo "===== KUBERNETES PODS ====="

kubectl get pods -A

echo ""

echo "=========================================="
echo " Kubernetes installation completed!"
echo "=========================================="

PART 1 - ARCHITECTURE AND END-TO-END FLOW
==========================================

INTERVIEWER:
"Explain the architecture and end-to-end flow of Argo CD
Image Updater."


ANSWER:
------------

Argo CD Image Updater is used to detect newer versions of
container images and update the image version used by an
Argo CD application.

The complete flow starts from the Docker Host, where the
developer builds a new Docker image.

The image is then pushed to Docker Hub.

Argo CD Image Updater checks Docker Hub for a newer image
version according to the configured update policy.

When a new version is detected, Image Updater updates the
image version in the Git repository.

Argo CD monitors this Git repository. When the desired
configuration changes, Argo CD detects the change and
deploys the updated configuration to the Kubernetes cluster.

Kubernetes then starts the application using the new Docker
image version.


END-TO-END FLOW:

    Docker Host
         |
         | Dockerfile
         |
         | docker build
         v
    Docker Image
         |
         | docker push
         v
    Docker Hub
         |
         | New image version detected
         v
    Argo CD Image Updater
         |
         | Updates image version
         v
    GitHub
         |
         | deployment.yaml
         v
    Argo CD
         |
         | Deploy / Sync
         v
    Kubernetes Cluster
         |
         v
    Application


EXAMPLE:

Initially:

    Docker Hub:
        myimage:v1.1.0

    GitHub deployment.yaml:
        image: myimage:v1.1.0

    Kubernetes:
        Application running v1.1.0


Now developer creates a new version:

    myimage:v1.1.1


Developer pushes it:

    Docker Host
         |
         v
    Docker Hub
         |
         v
    myimage:v1.1.1


Argo CD Image Updater detects:

    New version = v1.1.1


It updates the Git configuration:

    image: myimage:v1.1.0

                TO

    image: myimage:v1.1.1


Argo CD detects the Git change and deploys the new
configuration to Kubernetes.

Finally:

    Kubernetes
         |
         v
    Application running v1.1.1


So the complete flow is:

    BUILD
      ↓
    PUSH
      ↓
    DOCKER HUB
      ↓
    IMAGE UPDATER
      ↓
    GITHUB
      ↓
    ARGO CD
      ↓
    KUBERNETES
      ↓
    NEW APPLICATION VERSION

    myimage:v1.1.0

    v1.1.1 = newer version

-------------

Docker Hub is the container image registry.

Example:

    DOCKER HUB
       |
       +-- myimage:v1.1.0
       |
       +-- myimage:v1.1.1

---------

GitHub contains the Kubernetes configuration files.

Example:

    deployment.yaml
    service.yaml

Example:

    image: myimage:v1.1.0


GitHub represents the desired configuration.

-------------------------

Argo CD Image Updater checks the container image registry

    myimage:v1.1.0

    myimage:v1.1.1

PART 7 - ONE-MINUTE INTERVIEW ANSWER
============================================================

"Argo CD Image Updater is used to automate container image
updates in a GitOps environment.

First, we build a new Docker image on the Docker Host and
push it to Docker Hub.

Argo CD Image Updater checks the image registry and detects
the newer image version according to the configured update
policy.

It then updates the image version in the Git repository.

Argo CD monitors the Git repository, detects the change, and
deploys the updated configuration to the Kubernetes cluster.

Finally, Kubernetes runs the application using the new
container image version.

So the overall flow is:

Docker Host → Docker Hub → Argo CD Image Updater
→ GitHub → Argo CD → Kubernetes → Application."
