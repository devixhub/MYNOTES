EXPLAIN ARGO CD ARCHETITUTRE ?
Argo CD follows the GitOps approach, where Git is the single source of truth. 
The user makes changes only in Git, and those changes are used to deploy the
desired application state to the Kubernetes cluster.we have two component of 
argo cd one is application controller and another is repo server, The Repo Server gets the 
configuration from Git, while the Application Controller compares the Git state 
with the actual cluster state and reconciles any differences. If someone makes a 
manual change directly in the Kubernetes cluster, it is not considered the source of truth; 
Argo CD detects the difference and, when self-healing/synchronization is enabled, brings the cluster 
back to the state defined in Git. So, in our GitOps model, deployment changes should come from the Git side, 
not from manual cluster-side changes.

How to walk your class through it:

UI / CLI - the student or engineer opens the dashboard or types an argocd command.
API server - every request lands here first. It's the single entry point.
Dex (left) handles login/authentication; Redis (right) caches results so repeated requests are fast. Both are helpers to the API server, not separate paths.
Repo server - pulls the raw manifests from Git, processes any Helm/Kustomize templating, and renders final YAML.
App controller - takes that rendered YAML, compares it to what's actually running in Kubernetes, and applies the difference.

Key teaching point: the Repo server only talks to Git, and the App controller only talks to Kubernetes - each component has one job. That separation is what makes Argo CD reliable and easy to reason about.

What is Argo CD?
Argo CD is a GitOps continuous delivery tool for Kubernetes.
It continuously checks the configuration stored in Git and 
compares it with the actual state of the Kubernetes cluster.
GIT = DESIRED STATE / SOURCE OF TRUTH
KUBERNETES = ACTUAL STATE

gitOps?
GitOps is a methodology where Git is used as the single source of
truth for the desired state of applications and infrastructure. 
In our Kubernetes environment, developers make configuration changes in Git,
and Argo CD automatically detects those changes and synchronizes the Kubernetes 
cluster with the desired state defined in Git.

REPO SERVER ?
The Repo Server connects to GitHub and gets the application configuration/YAML files.
The Argo CD Repo Server is responsible for connecting to Git repositories, 
retrieving application configuration, and generating or rendering Kubernetes manifests
Repo Server
     ↓
CONNECTS TO GIT
     ↓
GETS APPLICATION CONFIGURATION

APPLICATION CONTROLLER ?
The Application Controller continuously monitors applications, 
compares the desired state from Git with the actual state in Kubernetes, 
and reconciles any differences.

GIT = SOURCE OF TRUTH ?
Git says what SHOULD BE RUNNING.
Kubernetes shows what IS CURRENTLY RUNNING.

What happens if someone changes Kubernetes manually?
Git is the source of truth. A manual cluster change does not become the 
desired state in Git. Argo CD detects the difference and, when reconciliation/self-healing is enabled, 
restores the cluster to the Git-defined state.

API Server in Argo CD?
The API Server is the main entry point of Argo CD.
Whenever a user interacts with Argo CD using the Web UI or CLI, the request first comes to the API Server.

What is Redis?
Redis is the caching component of Argo CD used to store frequently accessed
or computed information temporarily for faster access

NOTE-
Argo CD has multiple components. The UI or CLI is used by users to interact with Argo CD, 
and all requests come through the API Server. Dex is used for authentication 
and integration with external identity providers, while Redis is used as a cache. 
The Repo Server connects to the Git repository, fetches and renders the application manifests. 
The Application Controller compares the desired state from Git with the actual state in the Kubernetes cluster 
and applies or reconciles the required changes. Git acts as the source of truth, and Kubernetes is maintained 
according to the desired state defined in Git.
