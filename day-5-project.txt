1/In a traditional deployment,
the application runs directly on the host operating system along with its required runtime and dependencies
2/Docker is a containerization platform that packages an application along with its dependencies into a container,
providing an isolated and consistent environment for running the application
3/Kubernetes is a container orchestration platform used to
deploy, manage, scale, network, and maintain containerized applications across a cluster

WHAT IS THE DIFFERENCE BETWEEN DOCKER AND KUBERNETES?
Docker is mainly used to containerize and package applications, 
whereas Kubernetes is used to orchestrate and manage those containers, 
including deployment, scaling, networking, and self-healing.

WHY DO WE NEED KUBERNETES IF WE ALREADY HAVE DOCKER?
Docker can run containers, but when we have many containers across multiple servers,
managing them manually becomes difficult. Kubernetes automates deployment,
scaling, networking, load balancing, and recovery of those containers.

:::::::WHY KUBERNETES CAME:::::::

The biggest problem is that large production environments became too complex 
to manage with simpler container orchestration tools.
Imagine:

50 Microservices
500 Containers
20 Servers
Multiple Environments

Now you need:

Auto Scaling
Self Healing
Load Balancing
Rolling Updates
Rollback
Service Discovery
Secrets
Config Management
Storage
Monitoring
Multi-node management

Kubernetes provides a large ecosystem and strong automation around these requirements.
	
Docker is mainly used for containerization, while Docker Compose is useful for managing multiple containers, 
especially in development and smaller environments. Docker Swarm also provides container orchestration. However, 
as applications became more microservice-based and production environments became larger and more complex, 
organizations needed stronger automation for scaling, self-healing, rolling updates, service discovery, storage, 
security, and multi-node management

When I run kubectl apply -f deployment.yaml, the request first goes to the Kubernetes API Server. The API Server checks the 
request and stores the desired configuration in etcd.

Then Kubernetes controllers look at the desired state and determine what resources need to be created. For example, 
if I have a Deployment with 3 replicas, the Deployment creates or manages a ReplicaSet, and the ReplicaSet makes sure that 3 Pods 
are required.

The newly created Pods don't initially have a worker node. The Scheduler identifies these Pods and selects a suitable worker node
based on available resources and scheduling rules.

Once a Pod is assigned to a worker node, the Kubelet on that node notices the Pod assignment. Kubelet communicates with the 
Container Runtime, such as containerd or CRI-O, and asks it to create and start the required container. 
If the image is not already available on the node, the runtime pulls the image from the container registry.

After the container starts successfully, my application starts running inside the Pod. If I have a Kubernetes Service, 
it provides a stable way for users or other applications to reach the Pods.

After everything is running, Kubernetes doesn't just stop. The controllers continuously compare the desired state with the 
actual state. For example, if I requested 3 Pods and one Pod crashes, Kubernetes detects that only 2 are running and works to 
create a replacement Pod. This is how Kubernetes provides self-healing and maintains the desired state.	
	
	kubectl → API Server → ETCD → Controller → Scheduler → Kubelet → Container Runtime → Pod → Application

DATA PLANE    = APPLICATION RUNNING

Control Plane 
=============
This is the first thing you should remember.
Control Plane = Brain 
The control plane decides:
What should happen?
Where should it happen?
Is the cluster in the desired state?

It contains:
API Server  ->ITS GATE KEEPER WHO TAKE INFORMATION FROM ADMIN
Scheduler   → IT RUN24/7 Chooses the worker node
Controller Manager ->MAINTAIN THE POD STATE (REQUEST TO CREATE 5 POD IT WILL CREATE EXECT THAT NOT LESS & NOT MORE)
ETCD  ->TAKE THE INFORMATION FROM API SERVER STORE THE DATA IN KEY VALUE PAIR

Data Plane
==========
Workers 
Worker nodes actually run the application.
They contain:
Kubelet   --> ITS CONNECT WITH API SERVER AND TAKE THE INFORMATION CREATE THE RESOURCES HELP OF CRE

Kube-proxy  -->Kube-proxy handles Kubernetes Service networking. It helps route network traffic coming to a 
Service toward the appropriate Pod.

CRE (Container Runtime Environment)  -->CRE is responsible for actually creating, starting, and managing the 
containers on the Worker Node
